Key insight: cuBLAS leaves the INT ALU pipeline completely idle while waiting on memory. ZipGEMM converts that idle time into useful decompression work. A Tiny Concrete Example — Encode & Decode 8 BF16 numbers · if the abstract version isn't clicking, this will

Let's compress an 8-element row of weights step by step. We'll use real BF16 bit patterns to make every byte traceable.

  ━━━━━━━━━━━━ STEP 1: Original 8 BF16 weights ━━━━━━━━━━━━

   position p:        0      1      2      3      4      5      6      7
   value (decimal):   0.51   0.27   3.14   1.02   0.73   0.13   0.62   0.41
                      ───┐   ───┐   ───┐   ───┐   ───┐   ───┐   ───┐   ───┐
   sign  (1 bit):       0      0      0      0      0      0      0      0
   exp   (8 bits):    126    125    128    127    126    124    126    125    ← all between 124..127
   mant  (7 bits):    0x02   0x0A   0x49   0x05   0x3B   0x05   0x1E   0x52   except p=2

   Storage if uncompressed: 8 elements × 2 bytes = 16 bytes


  ━━━━━━━━━━━━ STEP 2: Decide what's "high-frequency" ━━━━━━━━━━━━

   Looking at exponents: {126, 125, 128, 127, 126, 124, 126, 125}
   The 7 most common values across the WHOLE matrix turn out to be 124..130.
   So we set:  start_exp = 123   (exponent codes 1..7 cover 124..130)

   For each position, classify:
     position p:           0     1     2     3     4     5     6     7
     exponent:           126   125   128   127   126   124   126   125
     is high-freq?        ✓     ✓     ✗     ✓     ✓     ✓     ✓     ✓
                                       ↑
                                128 is NOT in the 7 chosen "common" values
                                in this fictional example  →  goes to fallback


  ━━━━━━━━━━━━ STEP 3: Compute the 3-bit exponent code ━━━━━━━━━━━━

   For high-freq positions, code = exponent − start_exp = exponent − 123:
     position p:           0     1    2     3     4     5     6     7
     exponent − 123:       3     2    5     4     3     1     3     2
     code (binary):      011   010   XXX  100   011   001   011   010
                                       ↑

   Final 3-bit codes per position:
     position p:           0     1     2     3     4     5     6     7

   This is the trick — instead of storing each 3-bit code as a byte,
   we transpose them into 3 separate bitmaps (one per bit-plane):

                          p=0  p=1  p=2  p=3  p=4  p=5  p=6  p=7
     code (binary):       011  010  000  100  011  001  011  010

     bitmap1 (LSB):       1    0    0    0    1    1    1    0    →  0b01110001 = 0x71

       (0<<7)|0x05,    // p=3
       (0<<7)|0x3B,    // p=4
       (0<<7)|0x05,    // p=5
       (0<<7)|0x1E,    // p=6

   Thread wants weight at position p=4. It already has bitmaps in registers
   from a single LDS.U64 load. It runs:

     ① Extract the 3-bit code for p=4:
         bit1 = (0x71 >> 4) & 1 = 1
         bit2 = (0xCB >> 4) & 1 = 0
         bit3 = (0x10 >> 4) & 1 = 0
         code = (0 << 2) | (0 << 1) | 1 = 001 (= 1 in decimal)
                                                     wait — the code at p=4 should be 011 (= 3)
                                                     let me re-check using the correct bitmap reading...

     [Reading bitmap LSB-first: bitmap1 bit-4 = 1, bitmap2 bit-4 = 1, bitmap3 bit-4 = 0]
         code = (bit3<<2) | (bit2<<1) | bit1 = (0<<2)|(1<<1)|1 = 011 = 3  ✓

     ② Decide if high-freq:
         indicator = bitmap1 | bitmap2 | bitmap3 = 0x71|0xCB|0x10 = 0xFB
         is_high_freq = (0xFB >> 4) & 1 = 1 → high-freq

     ③ Reconstruct exponent:
         exp = start_exp + code = 123 + 3 = 126  ✓ (matches original)

     ④ Find the right index into SignMantissa[]:
         mask          = (1 << 4) − 1                 = 0x0F
         hf_before_p4  = popcount(0xFB & 0x0F)        = popcount(0x0B) = 3
         idx           = 3                              (skip the 3 hf elements before p=4)
         combined      = SignMantissa[3]              = (0<<7)|0x3B = 0x3B

     ⑤ Assemble final BF16:
         sign     = (0x3B >> 7) & 1            = 0
         mantissa = 0x3B & 0x7F                = 0x3B
         bf16     = (0<<15) | (126<<7) | 0x3B  = 0x3F3B
         decoded  = bfloat16(0x3F3B)           = 0.7305...  ✓ matches original 0.73

   Total instructions: ~3 LDS + ~10 ALU ops + 1 POPC.  No branch on common path.


  ━━━━━━━━━━━━ DECODE: how a thread reconstructs position p=2 (low-freq) ━━━━━━━━━━━━

     ① Extract code: code = 000   (all 3 bitmap bits at p=2 are 0)
     ② is_high_freq = (0xFB >> 2) & 1 = 0  → low-freq path
     ③ Find offset into CompressedFull[]:
         idx = pos − hf_before = 2 − popcount(0xFB & 0x03) = 2 − 2 = 0
         decoded = CompressedFull[0] = 3.14  ✓

How Exponent is Stored — the TCA-TBE trick · the question that's worth its own section

A natural question: "Doesn't ZipGEMM still need to move exponent bits to L2/SMEM?" The answer: no — exponent is encoded INSIDE the bitmaps and never exists as a separate array. This is the core of the TCA-TBE encoding.

  A BF16 element = 1 sign bit | 8 exponent bits | 7 mantissa bits

  ─────────────── For high-frequency elements (97% of weights) ───────────────

  ZipServ observation: across LLM weights, ~97% of elements share only 8 distinct exponent values.
  These 8 values form a contiguous range [start_exp, start_exp + 7].

  Encoding: assign each exponent value a 3-bit code (0..7), and store
  the 3 bits as bit-planes across 3 separate bitmaps:

      bitmap1[tile_idx] bit_p  ←──┐
      bitmap2[tile_idx] bit_p  ←──┼──  3-bit exponent code for element at position p
      bitmap3[tile_idx] bit_p  ←──┘

  Decode (3 instructions, all in shared mem & registers):
      uint8_t code = ((bitmap3 >> p) & 1) << 2
                   | ((bitmap2 >> p) & 1) << 1
                   | ((bitmap1 >> p) & 1);
      uint16_t exp_bits = (start_exp + code) << 7;     // start_exp ∈ register
      uint16_t bf16     = (sign << 15) | exp_bits | mantissa;

  ▶ COST OF EXPONENT IN DRAM/L2/SMEM: 0 bytes
    (the bitmap is dual-purpose — it tells you "is this position high-freq?"
     AND simultaneously encodes which of the 8 exponents it is)

  ─────────────── For low-frequency elements (3% outliers) ───────────────

  Stored as full BF16 in CompressedFull[] array (sign + exp + mantissa together).
  Cost: 2 bytes/element × 3% = 0.06 bytes/element amortized.

  ─────────────── start_exp itself ───────────────

  Single uint8_t scalar → passed as kernel argument
       __global__ void Kernel(..., const uint8_t start_exp, ...)
  Lives in: SM register (or constant cache)
  DRAM cost: 0 bytes (the kernel argument is part of the launch packet)

  ───────────── Net per-element storage breakdown ─────────────
       Sign + Mantissa  : 1 byte    × 97% = 0.97 B
       Bitmap (3-bit)   : 0.375 B   × 100% = 0.375 B
       Fallback BF16    : 2 bytes   × 3%  = 0.06 B
       Offsets          : ≪ 0.001 B (per-tile metadata)
       ───────────────────────────────────────────────────
       TOTAL                                ≈ 1.41 B/elem
       Original BF16                         = 2.00 B/elem
       Compression ratio                    ≈ 1.42×

Wait — Isn't the Bitmap Itself an Overhead? · the honest accounting

Yes. The bitmap costs 0.375 B/element (3 bit-planes per 8×8 tile). The trick is that this single 0.375 B/elem simultaneously serves two purposes — high-freq flag AND 3-bit exponent code. Compare against alternative encodings:

  ─────── Comparison of weight compression schemes (per BF16 element) ───────

  Scheme                          | Bytes/elem | DRAM reads/elem  | SIMT-friendly?
  ────────────────────────────────┼────────────┼──────────────────┼────────────────
  (0) Original BF16 (no compression) | 2.00       | 1 (LDG.U16)      | ✓ trivial
  (1) Naive: 1-bit flag + 1-byte exp| 2.06       | 3 (flag/exp/sm)  | ✗ branch + gather
  (2) Naive packed: 1-bit + 3-bit exp| 1.49       | 3 + bit-extract  | ✗ branch + gather
  (3) Huffman (zipNN-style)          | ~1.55      | 1 + var-length   | ✗ heavy serial decode
  (4) ZipServ TCA-TBE (this work)    | 1.41       | 2 (bitmap+sm)    | ✓ lock-step warp
  ────────────────────────────────┼────────────┼──────────────────┼────────────────

  ▶ TCA-TBE wins on BOTH bytes AND decode-speed simultaneously.

  Why? The bitmap is dual-purpose:
    • If (bit1 | bit2 | bit3) == 0 at position p  →  position p is low-freq
                                                     (read fallback BF16)
    • Otherwise                                   →  position p is high-freq,
                                                     exponent code = (b3,b2,b1)
                                                     read sign+mantissa byte

  So the SAME 3 bits of bitmap encode:
    1. "Is this position compressible?"  (the OR of all 3 bits)
    2. "Which of the 7 high-freq exponents?" (the value of the 3 bits, 1..7)
    Code value 0 is reserved as the low-freq sentinel.

  Naive scheme (2) needs to load:
    • 1 high-freq flag bitmap  →  1 LDS
    • 1 exponent-code array    →  1 LDS  (only meaningful for hf elements)
    • 1 sign+mantissa array    →  1 LDS
    Plus complex indexing: prefix-sum the flag bitmap to find the
    correct offset into the exp-code AND sign+mantissa arrays separately.

  TCA-TBE merges (flag) and (exp-code) into one bitmap → 1 fewer LDS,
  AND only 1 prefix-sum (one POPC) is needed for both tables.

  ───── So the "honest" answer to "doesn't bitmap have overhead?" ─────

  YES — bitmap costs 0.375 B/elem. But:
    • It REPLACES what would otherwise be ~0.49 B/elem (flag + packed exp)
    • It enables zero warp divergence (every lane decodes in lock-step)
    • It cuts one full DRAM round-trip per element
    • It makes the entire decode warp-uniform with just 3 LDS + ~10 ALU ops

  The bitmap is the *cheapest possible* metadata that simultaneously
  encodes presence + exponent + remains compatible with Tensor-Core-
  aligned 8×8/16×8 tile shapes used by mma.sync.m16n8k16.

  ───── Reality check: bitmap as a fraction of total DRAM bytes ─────

  For a typical 70B-class GEMM (M=57344, K=8192):
       Sign + Mantissa  : 458 MB   (69% of compressed weight)
       Fallback BF16    :  28 MB   ( 4%)
       Bitmap           : 176 MB   (27% of compressed weight)
       Offsets          : 230 KB   (≪ 1%)
       ──────────────────────────────────
       Compressed total : 662 MB   (vs 939 MB original = 1.42× compression)

  So the bitmap eats roughly a quarter of the compressed weight bytes.
  Without the bitmap-as-dual-purpose trick, that 27% would more than
  double (since you'd need separate flag + exp arrays), and compression
  ratio would drop from 1.42× to about 1.34×.

Why ZipGEMM Wins (or Loses) on Your GPU

✓ Where ZipGEMM advantages compound

  • 30% less DRAM traffic — 1.42× lossless compression on weights (TCA-TBE format)
  • At small N, weights are ~99% of total bytes moved → maximum benefit zone
  • INT ALU runs in parallel with Tensor Core → decompression is "free" ($0 TC cost)
  • cp.async (LDGSTS.128) bypasses L1, freeing L1 capacity for activations and metadata
  • Triple-bitmap layout → zero warp divergence, lock-step decode for all 32 threads
  • Larger M dimension → more thread blocks → better SM occupancy

✗ Where ZipGEMM costs / limits bite

  • ~15 INT ALU instructions per element of decompression overhead
  • Your GPU has ~1400 GB/s bandwidth — less bandwidth pressure than RTX5090 (1792 GB/s claimed in paper, but with smaller L2)
  • cuBLAS 12.8 ships Blackwell-tuned kernels; ZipGEMM uses Ampere-era PTX (no sm_120-specific tuning)
  • Tile shape tied to M dimension → Down_proj (small M, large K) wastes most of the GPU
  • At N≥128, system enters compute-bound regime → ALU work now competes with TC, no win possible
  • Bitmap overhead grows as O(M·K/64) → small matrices have high relative metadata cost
